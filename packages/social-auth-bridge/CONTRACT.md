# Social auth bridge contract

The bridge is a maintainer-operated HTTPS service. It owns the Meta application secret and short-lived OAuth state; the Desktop Host owns the PKCE verifier and durable local credential through Electron Main's OS-secure adapter.

`POST /v1/instagram/authorize` accepts the Host-generated `state`, S256 `codeChallenge`, and local social-account identifier. The bridge keeps the identifier only in the short-lived in-memory flow so the eventual media credential is bound to the requesting account; persistent credential records contain only its hash. The bridge returns an Instagram Login URL using the fixed professional-account scopes and its registered HTTPS callback. This endpoint is Host-to-bridge traffic and never accepts input from Renderer or Agent APIs.

`GET /v1/instagram/callback` consumes the state once, exchanges Meta's temporary authorization code, upgrades the token on the server, then redirects to `social-harness://oauth/callback` with the original state and an opaque, expiring, single-use handoff ticket. It does not issue a media credential. The callback must not log its query string or redirect URL.

`POST /v1/instagram/redeem` accepts the opaque ticket and Host-held PKCE verifier. After consuming a valid ticket, the bridge creates a new account-scoped media credential and returns it with the access token and expiry only for the authenticated pending Host flow. It keeps prior credentials active until the Host commits the new profile and tokens; no more than four credentials may be active for one account. Invalid, expired, replayed, or mismatched tickets fail closed and create no media credential. If media-credential persistence fails, redemption fails and the user must restart authorization. The desktop client calls this endpoint over outbound HTTPS and stores the response through Main. The bridge response is never forwarded to Renderer or Agent APIs.

`DELETE /v1/media/credential` revokes exactly the supplied credential and deletes account media only when no other media credential remains. The Host uses this after a successful reconnect to retire the previous key, or after failed verification to remove the newly issued key. `DELETE /v1/media/credentials` uses the currently stored credential to revoke every key for that account and delete all its temporary media on disconnect. Both endpoints authenticate solely with a Host-only bearer credential.

V1 state and tickets live in process memory, are bounded and expire after five minutes, and are invalidated by a process restart. Deploy one replica until a shared, expiring store is explicitly designed. Hosting, Meta app review, secret rotation, monitoring, TLS, and rate limits are maintainer responsibilities. The desktop release supplies the bridge origin so users do not configure hosting, a router, a tunnel, or a payment method.

The server persists only hashed media-upload credentials and bounded temporary-media manifests/files in private file-backed stores under `SOCIAL_AUTH_BRIDGE_DATA_DIR`. The credential index permits at most four hashed credentials per account and 20,000 accounts; per-key revocation retains other keys and account media, while revoke-all is used for disconnect. These stores survive a restart when the volume is mounted. A media capability becomes unreadable at its recorded expiry and reads do not extend its lease. `FileTemporaryMediaStore` owns a serialized expiry worker that sweeps every 60 seconds while the server is active, as well as cleanup during startup and media requests; failed sweeps are reported without account/media data and retried on the next interval. The worker stops when the server closes. OAuth state and handoff tickets are intentionally not persisted; interrupted sign-ins fail closed and can be restarted in the app. V1 does not require SQLite or a separate object-storage provider.
